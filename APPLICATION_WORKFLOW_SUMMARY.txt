1. TOPOLOGY (air-gapped LAN, no internet anywhere)
================================================================================
  Central Server PC                          Workstation PCs (any number)
  -----------------                          -----------------------------
  DeskAppServer.exe  (main.py --server-only)  DeskApp.exe  (main.py)
   - the ONLY process that opens               - login window -> role workspace
     data/central_app.db (SQLite, WAL)         - talks to the server only through
   - WebSocket server on TCP 8765                ws://<server-ip>:8765
   - authenticates every connection            - Heads: offline outbox
   - enforces every permission/filter            data/client_queue.db
   - daily backups to data/backups/            - remembers server IP and window
   - log file data/logs/server.log               layout (QSettings), log file
                                                 data/logs/client.log

  Rules
  - Clients never read central_app.db.
  - A normal launch never starts a server. "--standalone" (demo) starts an
    embedded server using a separate data_demo/ folder.
  - Identity comes from the authenticated session on the server, never from
    data a client sends.

3. DATABASES
================================================================================
A. data/central_app.db (server only). Schema version in PRAGMA user_version.
  disciplines        discipline_id PK, name, is_hidden, created_at
  users              user_id PK (fingerprint ID or name), full_name,
                     password_hash ("pbkdf2_sha256$600000$<hex>"),
                     password_salt, role (HEAD|ADMIN|COO|SUPER_ADMIN),
                     must_change_password, discipline_id (Heads only)
  projects           project_id PK, name, description, is_hidden,
                     is_deleted, deleted_at, deleted_by
  tasks              task_id PK (TSK-NN), project_id, name, description,
                     discipline_id, planned_start_date, planned_end_date,
                     assigned_head_id (optional: pin task to one Head),
                     proposed_by_id, is_hidden, is_deleted, deleted_at,
                     deleted_by
  progress_logs      log_id PK (client UUID), employee_id, project_id,
                     task_id, start_date, end_date, progress_percentage
                     (0-100), progress_stage (In Progress|Revision|Hold|Done),
                     entry_type (NEW|CONTINUATION|REVISION), revision_number
                     (server-assigned per task), notes, discipline_id (Head's),
                     assigned_to (free text), submitted_at (local time)
  task_proposals     proposal_id PK (client UUID), project_id, task_name,
                     proposed_by_id, discipline_id, planned dates, status
                     (PENDING|APPROVED|REJECTED), task_id (set on approval),
                     admin_id, rejection_reason, created_at, decided_at
  task_date_change_requests  request_id PK (client UUID), task_id,
                     requested_by_id, old/new start+end dates, reason, status,
                     admin_id, rejection_reason, created_at, decided_at
  priority_notifications  notification_id PK, coo_id, target_employee_id,
                     message, status (PENDING|ACCEPTED|DENIED), created_at,
                     responded_at
  user_sessions      token_hash PK (SHA-256 of session token), user_id,
                     created_at, expires_at
  system_settings    key PK, value, updated_at, updated_by
                     keys: backup_retention_count, backup_time,
                     password_min_length, session_lifetime_days
  employee_projects  legacy table, kept but no longer used

  Migrations (DBManager._migrate): v2 soft-delete columns + indexes;
  v3 old UTC log timestamps -> local time; v4 system_settings. Each step runs
  once, in a transaction, and never deletes data.

B. data/client_queue.db (each workstation)
  offline_queue      queue_id, user_id, event_type (SUBMIT_LOG|PROPOSE_TASK|
                     REQUEST_TASK_DATE_CHANGE|RESPOND_NOTIFICATION), item_id,
                     payload_json, status (PENDING|FAILED), last_error,
                     attempts, created_at

4. WORKFLOWS
================================================================================
4.1 Server start
  1. DBManager opens/creates central_app.db, runs migrations, seeds the 10
     disciplines and the Heads in data/seed_heads.json (idempotent; skips
     placeholders, duplicates and unknown disciplines; never overwrites).
  2. If there is no Super Admin, "superadmin" is created with a random one-time
     password; never-used legacy default accounts (admin/coo/superadmin with
     password = ID) get one too. Shown on the console and saved to
     data/FIRST_RUN_CREDENTIALS.txt.
  3. WebSocket server listens on 0.0.0.0:8765; BackupScheduler starts.

4.2 Login and first-login password change
  1. LoginDialog (server IP remembered) -> NetworkClient.login() opens the
     persistent connection and sends LOGIN {user_id, password, protocol}.
  2. Server checks the password (5 failures = 60 s lockout), binds a Session
     (identity/role/discipline from the DB) and returns a session token and
     the password policy.
  3. If must_change_password: PasswordChangeDialog -> CHANGE_PASSWORD on the
     same session (old password waived only for this forced change). Until
     then the server refuses every other action.
  4. AppController opens the role window. On a network drop the client
     reconnects and sends RESUME {session_token}; if the session was revoked
     (password reset) or expired, the user is returned to the login window.

4.3 Head: daily log
  - Project selector on top; the discipline tab lists only the Head's
    discipline tasks for that project (server-filtered; pinned tasks only for
    their Head).
  - Selecting a task prefills start/end date with the task's planned dates
    (from the approved request or a later date change; today if none) and
    shows "Planned: X to Y". The dates stay editable so a log records when
    the work really happened.
  - Form: start/end date, entry type (New/Continuation/Revision; the R-number
    preview comes from the server, the final number is assigned on save),
    progress stage and %, Assigned To, notes -> Submit.
  - SyncService writes the log to client_queue.db, sends SUBMIT_LOG, and
    deletes it only after the server confirms. Toast: "saved on the Central
    Server (R2)", "queued offline", or "rejected: reason".
  - Server validates everything (dates, stage, %, lengths, task belongs to the
    project and the Head's discipline, task active) and stores the row
    idempotently by log_id.

4.4 Offline queue
  - Offline: items stay PENDING; the red banner and badge say so.
  - Reconnect / every 30 s: items are sent in order. Server error codes
    FORBIDDEN/VALIDATION -> item becomes FAILED ("Rejected Items" button:
    Retry/Discard). Network errors -> retried later.
  - The queue is per user: another user on the same PC never sends it.

4.5 Task proposal (Head -> Admin)
  PROPOSE_TASK {proposal_id, project_id, task_name, dates} -> PENDING.
  Admin approves (creates task TSK-NN) or rejects with a mandatory reason.
  Only PENDING can be decided; approving twice is a no-op. The proposer and
  the managers get a DATA_CHANGED("proposals") event; all clients get
  DATA_CHANGED("tasks") on approval.

4.6 Date change request (Head -> Admin)
  REQUEST_TASK_DATE_CHANGE {request_id, task_id, new dates, mandatory reason}
  for a task in the Head's discipline. Approve updates the task's planned
  dates; reject needs a reason. Same PENDING-only rules as 4.5.

4.7 COO priority alert
  COO_NOTIFY {notification_id, target_employee_id, message} -> delivered at
  once if the Head is online, otherwise at their next login. The Head sees one
  blocking modal per alert (Accept/Deny only, cannot be closed otherwise).
  RESPOND_NOTIFICATION is accepted only from the targeted Head; the COO's
  tracker updates live and keeps history (GET_NOTIFICATIONS).

4.8 Admin
  Heads: create (initial password = ID), edit name/discipline, reset password
  (revokes their sessions). Projects: add / hide / delete. Tasks: add (with
  discipline, planned dates, optional pinned Head) / edit / hide / delete.
  Disciplines: add / hide. Delete = soft delete. Approvals (4.5, 4.6),
  analytics, project timeline, Excel export.

4.9 Super Admin
  Everything Admin and COO can do (their panels are embedded) plus: create and
  edit ADMIN/COO/SUPER_ADMIN accounts (the last Super Admin cannot be
  demoted) and System Settings (backup time and retention, password minimum
  length, session lifetime) with server status.

4.10 Excel export (server-side)
  EXPORT_EXCEL_REQUEST {project_id, discipline_id, employee_id, start_date,
  end_date}. The date range uses overlap: a log counts if its start-end period
  touches the range. Workbook: "All Logs", one sheet per discipline (when not
  filtered to one), "Report Info" (filters, rule, row count, generated
  at/by). Hidden/deleted projects, tasks and disciplines are labelled and shown
  in grey. Built on its own thread and sent in chunks.

4.11 Real-time updates
  After each change the server sends DATA_CHANGED {scopes} only to the roles
  and users concerned; screens reload only those scopes (debounced). New logs
  stream to Admin/COO/Super Admin as NEW_LOG_EVENT.

4.12 Backups, restore, recovery
  BackupScheduler: a backup at startup if none exists for today, then daily at
  backup_time. SQLite backup API, integrity-checked, newest N kept
  (central_app_YYYYMMDD_HHMMSS.db). With the server stopped:
  "DeskAppServer.exe --restore <file>" (saves the current DB as
  central_app_pre_restore_*.db first) and "--reset-superadmin".

5. SERVER ACTIONS AND PERMISSIONS  (H=Head A=Admin C=COO S=Super Admin)
================================================================================
  Public (no login):   PING, LOGIN, RESUME
  Any logged-in role:  LOGOUT, CHANGE_PASSWORD, GET_SNAPSHOT, GET_DISCIPLINES,
                       GET_PROJECTS, GET_TASKS, GET_PROJECT_TIMELINE
                       (Heads: own discipline only; hidden items for A/S only)
  H only:              SUBMIT_LOG, CALCULATE_NEXT_REVISION, PROPOSE_TASK,
                       REQUEST_TASK_DATE_CHANGE, RESPOND_NOTIFICATION
  H, A, S:             GET_TASK_PROPOSALS, GET_DATE_CHANGE_REQUESTS (H: own)
  H, C, S:             GET_NOTIFICATIONS (H: own)
  A, S:                APPROVE/REJECT_TASK_PROPOSAL, APPROVE/REJECT_DATE_CHANGE,
                       ADD_DISCIPLINE, TOGGLE_HIDE_DISCIPLINE, CREATE_USER,
                       UPDATE_USER, RESET_PASSWORD (A: Heads only),
                       ADD_PROJECT, TOGGLE_HIDE_PROJECT, DELETE_PROJECT,
                       ADD_TASK, UPDATE_TASK, UPDATE_TASK_DATES,
                       TOGGLE_HIDE_TASK, DELETE_TASK, GENERATE_NEXT_TASK_ID,
                       GET_ANALYTICS
  A, C, S:             GET_USERS (A and C: Heads only), GET_RECENT_LOGS,
                       EXPORT_EXCEL_REQUEST
  C, S:                COO_NOTIFY
  S only:              GET_SETTINGS, UPDATE_SETTINGS
  Error codes: AUTH_REQUIRED, SESSION_EXPIRED, PASSWORD_CHANGE_REQUIRED,
  FORBIDDEN, VALIDATION, UNKNOWN_ACTION, BAD_REQUEST, RATE_LIMITED, INTERNAL.
