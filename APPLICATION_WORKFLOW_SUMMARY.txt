1. ARCHITECTURAL TOPOLOGY & MULTI-PC AIR-GAPPED NETWORK DESIGN
================================================================================
DeskApp is engineered for strict air-gapped Local Area Networks (LAN) without
any external internet connectivity or third-party cloud infrastructure.

Topology Diagram:
--------------------------------------------------------------------------------
                         LOCAL AREA NETWORK (LAN)
                         
             [ Central Server Daemon ] (Port 8765)
             - Run via Launch_Server_Daemon.bat (main.py --server-only)
             - Sole process with read/write access to central_app.db (WAL mode)
             - Automated daily backups in data/backups/ (last 30 retained)
             - Handles authentication, business logic, role checks & exports
                           ^               ^               ^
                           |               |               |
             ws://IP:8765  |  ws://IP:8765 |  ws://IP:8765 |
                           v               v               v
             +---------------+   +---------------+   +---------------+
             | Head / Worker |   | Admin Portal  |   | COO / Super   |
             | Workstation   |   | Workstation   |   | Workstation   |
             | - Client only |   | - Client only |   | - Client only |
             | - Local Queue |   | - Full tasks  |   | - Live feed   |
             |   (client_queue|   | - Approvals   |   | - Modal alert |
             | - No direct DB|   | - No direct DB|   | - No direct DB|
             +---------------+   +---------------+   +---------------+

Key Structural Rules (Multi-PC Correctness):
1. Clients Never Read central_app.db Directly: Clients request all snapshots,
   tasks, users, analytics, and Excel exports over WebSockets.
2. Server-Enforced Authentication: The client connects to the Central Server
   first and verifies credentials over WebSocket (LOGIN action).
3. No Accidental Embedded Servers: Normal launches run as pure clients.
   The server only runs with --server-only (or --standalone for single-PC tests).
4. Reliable Queue with ACKs: Client generates UUIDs before queuing. Items are
   deleted from the client queue only upon receiving an ACK from the server.
   Duplicate submissions are handled idempotently.

2. TECHNOLOGY STACK & KEY DEPENDENCIES
================================================================================
- Language: Python 3.10+
- GUI Framework: PySide6 (Qt 6 for Python) with Dark Zinc & Purple QSS theme

3. CENTRAL & CLIENT DATABASE SCHEMAS
================================================================================

A. Central Database ("data/central_app.db" - Server Only)
--------------------------------------------------------------------------------
1. disciplines:
   - discipline_id (TEXT, PK): Code (URB, STR, INT, ARC, BIM, MEC, ELE, AI, QC, Infrastructure)
   - name (TEXT): Display title (Urban, Structure, Interior, etc.)
   - is_hidden (INTEGER, default 0): 0 = Active, 1 = Soft-deleted/hidden
   - created_at (TIMESTAMP)

2. users:
   - user_id (TEXT, PK): Unique ID / username (e.g. 1001, admin, coo)
   - full_name (TEXT): Display name (e.g. Eng. Karim Ashraf)
   - password_hash (TEXT): PBKDF2-HMAC-SHA256 hash (100,000 rounds)
   - password_salt (TEXT): 16-byte random salt hex
   - role (TEXT): 'HEAD', 'ADMIN', 'COO', 'SUPER_ADMIN'
   - must_change_password (INTEGER): 1 = Mandatory password change on login, 0 = Active
   - discipline_id (TEXT, FK -> disciplines): Head employee's assigned discipline
   - created_at (TIMESTAMP)

3. projects:
   - project_id (TEXT, PK): Project code (e.g. PRJ-01)
   - name (TEXT): Project title
   - description (TEXT): Project details
   - is_hidden (INTEGER, default 0): 0 = Active, 1 = Soft-hidden
   - created_at (TIMESTAMP)

4. tasks:
   - task_id (TEXT, PK): Task ID (e.g. TSK-01, auto-generated sequentially)
   - project_id (TEXT, FK -> projects)
   - name (TEXT): Task title
   - description (TEXT)
   - is_hidden (INTEGER, default 0)
   - proposed_by_id (TEXT, FK -> users): Attributed Head proposer (if proposed)
   - discipline_id (TEXT, FK -> disciplines): Department this task belongs to
   - planned_start_date (TEXT, YYYY-MM-DD): Target scheduled start
   - planned_end_date (TEXT, YYYY-MM-DD): Target scheduled end
   - assigned_head_id (TEXT, FK -> users): Assigned discipline Head (or NULL for all discipline Heads)
   - created_at (TIMESTAMP)

5. employee_projects:
   - employee_id (TEXT, FK -> users)
   - project_id (TEXT, FK -> projects)
   - assigned_at (TIMESTAMP)
   - PRIMARY KEY (employee_id, project_id)

6. progress_logs:
   - log_id (TEXT, PK): Unique UUID (e.g. LOG-XXXXXXXX)
   - employee_id (TEXT, FK -> users)
   - project_id (TEXT, FK -> projects)
   - task_id (TEXT, FK -> tasks)
   - start_date (TEXT): Actual work start date
   - end_date (TEXT): Actual work end date
   - progress_percentage (INTEGER): 0 - 100
   - progress_stage (TEXT): 'In Progress', 'Revision', 'Hold', 'Done'
   - entry_type (TEXT): 'NEW', 'CONTINUATION', 'REVISION'
   - revision_number (INTEGER): Incremental rework index (0 for new, 1..N for rework)
   - notes (TEXT): Activity notes & blockers
   - discipline_id (TEXT, FK -> disciplines): Snapshot of discipline at time of log
   - assigned_to (TEXT): Free-text name of team member who executed task
   - submitted_at (TIMESTAMP)
   - sync_status (TEXT): 'SYNCED'

7. priority_notifications:
   - notification_id (TEXT, PK): NOTIF-XXXXXXXX
   - coo_id (TEXT, FK -> users)
   - target_employee_id (TEXT, FK -> users)
   - message (TEXT)
   - status (TEXT): 'PENDING', 'ACCEPTED', 'DENIED'
   - created_at (TIMESTAMP)
   - responded_at (TIMESTAMP)

8. task_proposals:
   - proposal_id (TEXT, PK): PROP-XXXXXXXX
   - task_id (TEXT): Pre-allocated ID (e.g. TSK-04)
   - project_id (TEXT, FK -> projects)
   - task_name (TEXT)
   - proposed_by_id (TEXT, FK -> users)
   - discipline_id (TEXT, FK -> disciplines): Automatically tagged from Head's discipline
   - planned_start_date (TEXT)
   - planned_end_date (TEXT)
   - status (TEXT): 'PENDING', 'APPROVED', 'REJECTED'
   - admin_id (TEXT)
   - rejection_reason (TEXT): Mandatory if rejected
   - created_at (TIMESTAMP)
   - decided_at (TIMESTAMP)

9. task_date_change_requests:
   - request_id (TEXT, PK): DCR-XXXXXXXX
   - task_id (TEXT, FK -> tasks)
   - requested_by_id (TEXT, FK -> users)
   - old_start_date (TEXT)
   - old_end_date (TEXT)
   - new_start_date (TEXT)
   - new_end_date (TEXT)
   - reason (TEXT): Mandatory justification from Head
   - status (TEXT): 'PENDING', 'APPROVED', 'REJECTED'
   - admin_id (TEXT)
   - rejection_reason (TEXT): Mandatory feedback from Admin if rejected
   - created_at (TIMESTAMP)
   - decided_at (TIMESTAMP)

B. Client Offline Database ("data/client_queue.db" - Local Workstation)
--------------------------------------------------------------------------------
1. offline_queue:
   - queue_id (INTEGER, PK AUTOINCREMENT)
   - event_type (TEXT): 'SUBMIT_LOG', 'RESPOND_NOTIFICATION', 'PROPOSE_TASK', etc.
   - payload_json (TEXT): Serialized JSON payload containing generated UUID
   - created_at (TIMESTAMP)

4. CORE BUSINESS WORKFLOWS
================================================================================

4.1 Multi-PC Server Boot, Standalone Mode & Daemon Operation
--------------------------------------------------------------------------------
- Dedicated Central Server:
  * Launched via Launch_Server_Daemon.bat (main.py --server-only --port 8765).
  * Runs headlessly without GUI.
  * Manages database backups and real-time WebSocket communication.
- Workstation GUI Clients:
  * Launched via Launch_DeskApp.bat (main.py).
  * Runs as pure clients; never starts an embedded server by accident.
- Standalone Testing Mode (--standalone):
  * Starts embedded server + GUI client in a single process for local development.

4.2 Server-Side Authentication & Forced Password Reset
--------------------------------------------------------------------------------
1. LoginDialog opens and retrieves remembered Server IP from client QSettings.
2. User enters User ID, Password, and Server IP -> clicks Login.
3. Client establishes WebSocket handshake to ws://<server-ip>:8765 and sends
   {"action": "LOGIN", "payload": {"user_id": ..., "password": ...}}.
4. Central Server verifies credentials against central_app.db.
5. If server is unreachable, displays: "Cannot reach Central Server at <IP>".
6. If must_change_password == 1, PasswordChangeDialog forces new password
   entry via server action CHANGE_PASSWORD before workstation access.

4.3 Discipline (Departmental) Engine & Multi-Head Assignment
--------------------------------------------------------------------------------
- Ten standard disciplines:
  Urban (URB), Structure (STR), Interior (INT), Architectural (ARC), BIM (BIM),
  Mechanical (MEC), Electrical (ELE), AI (AI), QC (QC), Infrastructure (Infrastructure).
- Multiple Heads can belong to the same discipline (e.g. two BIM Heads).
- Initial Heads are seeded from data/seed_heads.json. Any placeholder IDs
  (<FINGERPRINT_ID>), empty entries, or duplicates are skipped with warnings.
- Server-Enforced Discipline Filtering:
  * In INITIAL_SNAPSHOT and GET_TASKS, server filters tasks to Head's discipline.
  * In SUBMIT_LOG, server rejects any log for a task outside Head's discipline.
  * Heads with no discipline see an empty task list with "Contact Admin".

4.4 Per-Task Planned Schedules & Date Change Approval Workflow
--------------------------------------------------------------------------------
- Tasks hold planned_start_date and planned_end_date.
- Admins set planned dates on task creation and can edit directly.
- Heads cannot edit dates directly. Instead, click "Request Date Change" ->
  enters new dates and mandatory justification reason.
- Request is dispatched (REQUEST_TASK_DATE_CHANGE) and appears in Admin's
  "Date Change Requests" sub-tab with badge count.
- Admin Approves: Task dates update in DB, broadcasts GLOBAL_DATA_REFRESH.
- Admin Rejects: Mandatory reason entered, requesting Head receives toast alert.
- Audit history is preserved in task_date_change_requests.

4.5 Employee (Head) Workstation: Progress Logging, Rework Counter & Autocomplete
--------------------------------------------------------------------------------
- Top: Project selector.
- Below: Discipline tab showing Head's discipline tasks with count (e.g. Structure (12)).
- Dates, Status, Notes, and Task Logging Context (New, Continuation, Revision).
- Rework iterations (R1, R2, R3...) calculated sequentially.
- "Assigned To" free-text field (max 100 chars) for team member names.
  Remembers last entered values per user via QSettings with QCompleter.

4.6 Task Proposal, Auto-ID Generation & Audit Sequence Timeline
--------------------------------------------------------------------------------
- Head clicks "+ Request Task" -> TaskProposalDialog automatically tags
  proposal with Head's discipline and auto-generates next ID (TSK-XX).
- Appears under Admin "Pending Approvals" tab.
- Admin Approves -> Task inserted into tasks table with origin attribution [By: Name].
- Admin Rejects -> Mandatory rejection reason provided.
- Both Head and Admin view full history in Audit Timeline.

4.7 Urgent COO Executive Oversight & Blocking Priority Modal
--------------------------------------------------------------------------------
- COO monitors real-time submissions feed (including "Assigned To" column).
- COO dispatches urgent priority alert to target Head employee.
- BlockingCenterModal pops up on Head's workstation:
  * Window close (Alt+F4) and ESC key are disabled.
  * Head must explicitly click ACCEPT or DENY.
- Response delivers live back to COO tracker.

4.8 Admin & Super Admin Roles, Permissions & Lifecycle Management
--------------------------------------------------------------------------------
- Server Role Enforcement:
  * Admin can create and manage HEAD accounts only.
  * Super Admin can create and manage ADMIN, COO, HEAD, and SUPER_ADMIN accounts.
- Soft-Delete / Hide Toggle for projects, tasks, and disciplines.

4.9 Reliable ACK-Based Offline Auto-Sync Engine
--------------------------------------------------------------------------------
- Client generates UUID log_id before queuing in client_queue.db.
- Submissions are sent to server if online, or queued if offline.
- Server returns ACK upon database write.
- Client deletes item from queue ONLY after receiving ACK.
- Duplicate resends are handled idempotently by server.

4.10 Analytics & Performance Insights Engine
--------------------------------------------------------------------------------
- Metrics cards: Total Logs, Total Revisions, Active Projects, Active Heads.
- Employee Rework Breakdown: New Tasks vs Continuations vs Revisions.
- Project Task Status Breakdown: Done, In Progress, Hold, Revisions.

4.11 Server-Generated Multi-Sheet Excel Reports with Discipline Filtering
--------------------------------------------------------------------------------
- Server generates styled XLSX reports via openpyxl.
- Includes Task Discipline, Head Discipline, and Assigned To columns.
- Discipline = All creates "All Logs" sheet plus one sheet per discipline.
- Binary sent to client over WebSocket -> client opens Save As dialog.

4.12 Resizable & Collapsible Panel Design System
--------------------------------------------------------------------------------
- All workspaces use QSplitters for flexible layout resizing.
- CollapsiblePanel wraps panels with chevron toggle button (▼ / ◀ / ▲).
- Splitter sizes and collapsed states saved/restored per user in QSettings.

4.13 Automated Daily SQLite Backups & Retention
--------------------------------------------------------------------------------
- Central Server triggers backup on boot and daily using SQLite backup API.
- Stores in data/backups/central_app_YYYYMMDD.db.
- Automatically retains last 30 daily copies.

6. DEVELOPER CHEAT SHEET: EXTENDING & MODIFYING FEATURES
================================================================================

1. Adding a Database Column:
   In DBManager.init_db(), check PRAGMA table_info(table_name).
   If column is missing, run ALTER TABLE table_name ADD COLUMN col_name TYPE.

2. Adding a New WebSocket Action:
   - Server: Add branch in CentralWebSocketServer.handle_message().
   - Client: Use net_client.send_action("ACTION", payload). Handle response in
     response_received signal.

3. Adding a New Discipline:
   Add to DEFAULT_DISCIPLINES in config.py, or use Admin "Disciplines Management" tab.

4. Testing Changes:
   Run automated test suite:
   python -m pytest
