# DeskApp Audit Report (Phase 1)

Date: 2026-10-12
Scope: working tree on `main` at `0919b92` **plus the uncommitted changes** (about 4,700 changed lines across 15 files, plus the new files `timeline_widget.py`, `rebuild_db.py`, `APPLICATION_WORKFLOW_SUMMARY.txt` and `data/`). Everything below describes the code as it currently sits on disk.
No source code was modified during this audit.

---

## 1. Summary

**What works**

- **Login:** the client no longer reads `central_app.db`. Login and password change go to the server over WebSocket. The server IP is remembered in QSettings.
- **No embedded server:** a normal launch does not start one. An embedded server only starts with `--standalone`.
- **Head task filtering:** the server's `GET_TASKS` and its initial snapshot filter tasks by the Head's discipline, provided the identity on the socket is honest.
- **Workflows that run end to end:**
  - task proposals
  - date-change requests (rejection reason required)
  - COO alerts, with a modal that cannot be dismissed
  - per-discipline Excel sheets with "(Hidden)" labels
  - QSplitter / collapsible panels
- **Idempotent inserts:** logs, proposals and date-change requests are keyed on IDs generated by the client.
- **Seeding:** `seed_heads.json` seeding is idempotent and skips placeholder and duplicate IDs.
- **Migration:** migrating an old DB works. A DB created by the initial commit's code (`5b3b15a`) opened cleanly with the current code, and the new columns were added.
- **Tests:** all 15 existing tests pass (`pytest`: 15 passed in 29.7 s).
- **Build:** the PyInstaller build succeeds, and `DeskApp.exe --server-only` starts and listens.

**What is broken**

- **Security model:**
  - The server has no authenticated session. Any socket can claim any user and role with `IDENTIFY`, or send privileged actions without identifying at all.
  - An anonymous client can reset any password, including `superadmin`.
  - An anonymous client can create ADMIN and COO accounts and submit logs as any Head.
  - All of this was reproduced against a live server (Section 3).
- **Blocking calls on the server event loop:** every DB call and the Excel export run synchronously there. An export of about 6k logs blocks the server for about 19 s. An export of 15k logs blocks it for about 50 s. Every connected client is dropped by keepalive timeout while this happens. Reproduced.
- **Data integrity:**
  - The revision counter is trusted from the client.
  - Approvals have no state machine: double approval creates duplicate tasks.
  - Foreign keys are not enforced.
  - WAL is not enabled.
  - Analytics counts are inflated by the number of tasks in each project (4x in the test).
- **Spec gaps:**
  - There is no real Delete (soft delete) for projects or tasks, only Hide.
  - There is no progress percentage input.
  - Excel export filters are incomplete.
  - Weak default accounts (`admin/admin`, `coo/coo`, `superadmin/superadmin`) are always seeded. The current `data/central_app.db` also holds demo data (`1001`, Project Alpha/Beta).

**Overall risk: HIGH.** The app works for one honest user at a time on a small dataset. It is not safe for real multi-PC use. Anyone on the LAN can take over admin accounts, and one large export disconnects everyone.

## 2. How the code is organized

| Layer | File | Notes |
|---|---|---|
| Entry point | `main.py` | `--server-only` runs `asyncio.run(server)`. GUI mode runs qasync loop → `LoginDialog` → role workspace → loops on logout. `--standalone` starts an embedded server and seeds demo data. |
| Config | `app/core/config.py` | `BASE_DIR` is `dist/..` when frozen inside `dist/DeskApp`, else the exe dir. Holds `data/`, `data/backups/`, roles, stages and 10 disciplines (adds `Infrastructure`). |
| Auth | `app/core/auth.py` | PBKDF2-SHA256, 100k iterations, 16-byte salt. Comparison is not constant-time. |
| DB | `app/database/db_manager.py` | `DBManager` (central) and `ClientQueueDBManager` (client queue). Opens a new connection per call, with no PRAGMAs. Migrations are ad-hoc `ALTER TABLE ADD COLUMN` checks; there is no schema version. |
| Server | `app/network/server.py` | One `if/elif` chain covering 38 actions. In-memory `clients` map: ws → {user_id, role, discipline_id}. |
| Client | `app/network/client.py` | `NetworkClient(QObject)`: reconnect loop, send queue, `response_received(type, data)` broadcast to every listener. Login and password change open separate one-off connections run in a thread and wait on `.result()`. |
| Sync | `app/services/sync_service.py` | Writes to `client_queue.db` first, sends, and deletes the item on `ACK` with status SUCCESS. Flushes everything on reconnect. |
| Excel | `app/services/excel_service.py` | Builds the workbook on the server: "All Logs" sheet plus one sheet per discipline. Bytes are base64-encoded into a single WebSocket frame. |
| UI | `app/ui/*.py` | `HeadWorkspace`, `AdminWorkspace`, `CooWorkspace`, `SuperAdminWorkspace` (embeds Admin and COO), `components.py`, `timeline_widget.py`, `styles.py`. |
| Tooling | `DeskApp.spec`, `Launch_*.bat`, `rebuild_db.py`, `tests/test_app.py` | `rebuild_db.py` **deletes the live DB** and seeds demo data. |

**WebSocket actions (client → server):**

- **Auth:** `LOGIN`, `CHANGE_PASSWORD`, `IDENTIFY`
- **Logs:** `SUBMIT_LOG`, `CALCULATE_NEXT_REVISION`, `GENERATE_NEXT_TASK_ID`
- **Task proposals:** `PROPOSE_TASK`, `APPROVE_TASK_PROPOSAL`, `REJECT_TASK_PROPOSAL`, `GET_TASK_PROPOSALS`
- **Date changes:** `REQUEST_TASK_DATE_CHANGE`, `APPROVE_DATE_CHANGE`, `REJECT_DATE_CHANGE`, `GET_DATE_CHANGE_REQUESTS`
- **COO alerts:** `COO_NOTIFY`, `RESPOND_NOTIFICATION`
- **Disciplines:** `GET_DISCIPLINES`, `ADD_DISCIPLINE`, `TOGGLE_HIDE_DISCIPLINE`
- **Users:** `GET_USERS`, `CREATE_USER`, `UPDATE_USER`, `RESET_PASSWORD`
- **Projects and tasks:** `GET_PROJECTS`, `ADD_PROJECT`, `TOGGLE_HIDE_PROJECT`, `GET_TASKS`, `ADD_TASK`, `UPDATE_TASK`, `UPDATE_TASK_DATES`, `TOGGLE_HIDE_TASK`, `GET_PROJECT_TIMELINE`
- **Reporting:** `GET_ANALYTICS`, `EXPORT_EXCEL_REQUEST`, `GET_RECENT_LOGS`

**Server → client messages:**

- **Snapshot and ACKs:** `INITIAL_SNAPSHOT`, `ACK`, `*_RESPONSE`
- **Events:** `NEW_LOG_EVENT`, `COO_PRIORITY_ALERT`, `NOTIFY_DISPATCH_CONFIRMATION`, `NOTIFICATION_RESPONSE_EVENT`, `NEW_TASK_PROPOSAL_EVENT`, `TASK_PROPOSAL_DECIDED_EVENT`, `TASK_DATE_CHANGE_EVENT`, `GLOBAL_DATA_REFRESH`

**Schema** (as actually created): `disciplines`, `users`, `projects`, `tasks` (with `discipline_id`, `planned_*`, `assigned_head_id`, `proposed_by_id`), `employee_projects` (populated but never used to filter anything), `progress_logs` (with `entry_type`, `revision_number`, `discipline_id`, `assigned_to`, `progress_percentage`), `priority_notifications`, `task_proposals`, `task_date_change_requests`. There is no `is_deleted` column anywhere. The client DB has a single table, `offline_queue`.

**How each workspace gets its data:** only through server actions. No client opens `central_app.db`. `db_manager` is passed as `None` to every workspace.

## 3. What I ran

1. **Test suite.** System Python 3.10.2: `python -m pytest`, 15/15 pass. There is no `requirements.txt` or `pyproject`, so I did not build a venv from a pinned set. The installed versions are PySide6 6.11.2, qasync 0.28.0, websockets 12.0, openpyxl 3.1.2, PyInstaller 5.13.0.
   **Side effect:** `test_database_backup` writes into the **real** `data/backups/` folder because `BACKUPS_DIR` is module-global. Running the suite created `data/backups/central_app_20261012.db`, which contains the test fixture DB. I could not delete it (blocked by a permission rule), so please delete it yourself (see finding F-29).
2. **Live server.** I copied the app into the scratchpad, so it had its own `data/` folder, and ran `main.py --server-only --port 18765` there. Then I ran a protocol-level script (`probe.py`) with several simultaneous sockets standing in for an anonymous LAN host, Admin, COO and Heads. I did not drive the GUI; every flow was exercised through its protocol action.
3. **Load test.** I loaded 6k and then 15k logs and requested an export while a "bystander" client using the real client's keepalive settings (`ping_interval=10`, `ping_timeout=5`) stayed connected.
4. **Migration.** I built a DB with the initial commit's `db_manager.py` and opened it with the current `DBManager`.
5. **Build.** I ran PyInstaller with the repo spec into a temp folder. Build OK, 240 MB, includes numpy. The frozen `--server-only` started and listened.

## 4. Findings

Severity: **Critical** = security breach, data loss or system-wide outage. **High** = wrong data or a broken core workflow. **Medium** = spec gap or degraded behavior. **Low** = hygiene.

| ID | Area | Sev | Description | Evidence | Impact on users |
|---|---|---|---|---|---|
| F-01 | Auth / sessions | Critical | The server trusts `IDENTIFY {user_id, role}` from any socket. No password and no session token. The role comes from the payload, not the DB. | `server.py:131-141`; probes 2 and 12 | Anyone on the LAN can act as Super Admin, Admin or COO. A Head can see every discipline. |
| F-02 | Auth | Critical | `CHANGE_PASSWORD` with `force: true` skips verification for any user, even without login. The UI itself always sends `force=True`. | `server.py:110-129`, `db_manager.py:555-574`, `login_dialog.py:75`; probe 4 | Any account, including `superadmin`, can be taken over in one message. |
| F-03 | Authorization | Critical | No per-action role checks. The only check is in `create_user`/`update_user`/`reset_user_password`, and only for `actor_role == ADMIN`. When `actor_role` is `None` (anonymous) every check is skipped. Approvals, project/task CRUD, discipline CRUD, analytics, export, user listing and recent logs are open to everyone. | `server.py:224-643`; `db_manager.py:482`; probes 3, 5, 9, 10 | Heads can approve their own requests. Anonymous clients can create accounts and read all data. |
| F-04 | Identity spoofing | Critical | The acting user is taken from the payload (`employee_id`, `admin_id`, `coo_id`, `proposed_by_id`, `requested_by_id`), not from the session. `RESPOND_NOTIFICATION` does not check that the responder is the target. | `server.py:144-386`; `db_manager.py:1019-1078, 1139-1152`; probes 6 and 13 | Logs and decisions can be forged in another person's name, and the audit trail can't be trusted. |
| F-05 | Server concurrency | Critical | All SQLite work and the Excel build run synchronously inside the asyncio handler. Export takes about 19 s at 6k logs and 50 s at 15k. Clients ping every 10 s with a 5 s timeout, so every client disconnects during an export, including the one that asked for it. | `server.py:610-634`, `excel_service.py`; probe 15 | One export disconnects the whole office. Exports fail once there is enough data. |
| F-06 | Export transport | High | The export is sent as a single base64 JSON frame. websockets' default `max_size` is 1 MiB on both ends, so a workbook above about 750 KB is rejected. That is about 6k logs with short notes, fewer with long notes. | `server.py:619-626`, `client.py:43`; measured 6.1 MB base64 at 15k logs | Exports stop working as data grows. |
| F-07 | Default credentials | High | `superadmin/superadmin`, `admin/admin` and `coo/coo` are always seeded, in every mode. The real `data/central_app.db` also contains demo Head `1001` and demo projects and tasks. `must_change_password` is enforced only in the client UI. | `db_manager.py:249-317`; `rebuild_db.py`; inspected `data/central_app.db` | Trivial takeover on any fresh install. Demo data appears in production. |
| F-08 | Forced password change | High | The server allows every action for users with `must_change_password=1`. Minimum-length and complexity rules do not exist. Passwords are `.strip()`ped. | `server.py:77-108`; `login_dialog.py:58,181` | The first-login policy can be bypassed with a raw client. Weak passwords are accepted. |
| F-09 | Error handling | High | `handler()` catches only `ConnectionClosedError`. Any exception in `handle_message` (bad payload, `int('abc')`, `None.strip()`, DB locked) closes the socket with 1011. Many write actions only `logger.error` on failure and never reply: `ADD_PROJECT`, `TOGGLE_*`, `UPDATE_TASK`, `UPDATE_TASK_DATES`, `APPROVE_*`, `REJECT_*`, `ADD_DISCIPLINE`, `COO_NOTIFY`. The UI then shows a success toast anyway. | `server.py:671-679`, plus the `except` blocks listed; probe 14 | Users see "success" for changes that never happened. One bad packet disconnects a client. |
| F-10 | Offline queue | High | (a) An `ACK` with `status: ERROR` leaves the item queued forever. It is resent on every reconnect and never shown to the user. (b) Only 4 action types are persisted. Admin and COO actions sent while offline sit in an in-memory `asyncio.Queue` and are lost when the app closes. A packet already taken off the queue is dropped if `ws.send` fails. (c) The Head toast says "submitted successfully" before any ACK arrives. (d) The queue belongs to the PC, not the user, so after a logout the next user's session flushes the previous user's items. (e) There is no visible list of failed items and no retry or backoff policy. | `sync_service.py:228-317`, `client.py:109-131`, `head_workspace.py:570-578` | Logs the user believes are saved can sit unsent forever or be lost silently. Admin edits made during a network blip vanish. |
| F-11 | Idempotency key | High | Client IDs are only 32 bits (`LOG-` + 8 hex). Duplicate checks match on `log_id` alone and return the *existing* row with ACK SUCCESS. A collision therefore drops a different log silently. There is about a 50% chance of at least one collision by around 77k logs. | `head_workspace.py:555`, `sync_service.py:235`, `db_manager.py:1054-1058` | Silent loss of logs over the life of the system. |
| F-12 | Revision counter | High | The R-number is computed by the client from a label (`lbl_rev_tag`) and stored as sent. Offline it defaults to R1. Two submissions before a refresh get the same R. The counter is scoped to (employee, project, task), so two Heads on the same task each start at R1. | `head_workspace.py:498-546`, `db_manager.py:1008-1029`; probe 8 | Revision tags in reports are wrong or duplicated. |
| F-13 | Approval state machine | High | Approve and reject never check `status = 'PENDING'`. Double approval inserts a second task. Reject after approve leaves the task in place. Approving a date change twice re-applies it, and rejecting it afterwards leaves the dates changed. Rejecting an unknown ID silently does nothing. | `db_manager.py:812-976`; probes 10 and 11 | Duplicate tasks and contradictory audit history. |
| F-14 | SQLite configuration | High | Journal mode is `delete`, not WAL (verified on `data/central_app.db`). There is no `busy_timeout` and `foreign_keys` is off, so declared FKs are not enforced. A new connection opens per call and multi-step writes are not in one transaction. Task ID generation (`max(TSK-n)+1` over tasks *and* proposals) runs in a separate connection, which is racy, and proposals reserve IDs, leaving gaps. | `db_manager.py:25-32, 758-774, 777-810`; probe 7 | Orphan logs, "database is locked" errors under load, colliding or skipped task IDs. |
| F-15 | Analytics correctness | High | `project_breakdown` joins `projects → tasks` and `projects → logs` at the same time, so every log sum is multiplied by the number of tasks in the project. | `db_manager.py:1200-1213`; probe 16 (60000 reported vs 15000 actual) | Management dashboards show wrong numbers. |
| F-16 | Soft delete | High | Delete does not exist for projects or tasks; only Hide/Unhide. The spec asks for Delete (removed from the UI forever, record and logs kept) as an action separate from Hide. | `db_manager.py:605-611, 750-756`; `admin_workspace.py` (no delete action) | An admin requirement is missing. |
| F-17 | Response routing | High | Every `*_RESPONSE` goes to every listener with no `msg_id` correlation. `SuperAdminWorkspace` embeds `AdminWorkspace` and `CooWorkspace`, so one `EXPORT_EXCEL_RESPONSE` opens two Save dialogs. The COO's `GET_USERS{role:HEAD}` reply overwrites the Super Admin's and Admin's full user lists, depending on which reply arrives last. | `client.py:103-104`; `superadmin_workspace.py:58-69`; `coo_workspace.py:144-157`; `admin_workspace.py:91-125` | Super Admin sees duplicate dialogs and user tables that randomly show only Heads. |
| F-18 | Backups | High | The backup runs only at server start, so a server that stays up for weeks never backs up again. A same-day restart overwrites that day's file. Pruning sorts `central_app_*.db` by name, which mixes in the `pre_rebuild` files. Backups sit on the same disk with no restore procedure. Tests write into the real backup folder. | `server.py:23-24`, `db_manager.py:376-400` | No real daily backups, and no tested restore. |
| F-19 | Frozen-exe server | High | The spec builds with `console=False`, but `--server-only` relies on console output and `input()` (port in use). There is no log file anywhere. Launched from the `.bat` or Explorer, the daemon shows nothing, and `input()` with no stdin will raise. `seed_heads.json` is not bundled, and the data folder location depends on the folder name (`dist/DeskApp` → `../../data`). Needs a test on the real target PC: in this environment the stdio was piped, so the output was visible. | `DeskApp.spec:30`, `main.py:103-120`, `config.py:5-13` | IT can't tell whether the server is running or why it failed. |
| F-20 | GUI blocking | Medium | Login and password change call `ThreadPoolExecutor(...).result()` on the Qt thread, which freezes the UI for up to 3.5–4 s. Login uses a throwaway connection; the long-lived connection then re-`IDENTIFY`s with no credentials, which is the root cause of F-01. | `client.py:186-210`, `login_dialog.py:194` | The UI freezes during login, and the design cannot be secured as it stands. |
| F-21 | COO alert modal | Medium | Every `GLOBAL_DATA_REFRESH` makes the Head re-`IDENTIFY`. The server then re-sends the snapshot with all PENDING alerts, and `on_initial_snapshot` opens a new modal for each, even while one is already open (`exec()` runs a nested event loop). On reconnect, the snapshot can arrive before the queued response is processed. The COO's response table only shows live events, not history. | `head_workspace.py:436-449, 640-650`; `coo_workspace.py:190-205` | Heads get stacked duplicate alerts. The COO loses track of responses after a restart. |
| F-22 | Head log form | Medium | There is no progress-percentage input (hard-coded `0`), so timeline progress is always 0% until "Done". Start ≤ end is not validated. The project selector is a side list rather than "on top". There is a single discipline tab. The toast is inline at the top, not at the bottom. | `head_workspace.py:269-291, 554-568`; `components.py:8-31` | Progress reporting is meaningless, and the UI doesn't match the spec. |
| F-23 | Excel export | Medium | The COO export has no filters. The Admin export has project, discipline and Head filters but **no date range** in the UI. The server date filter (`start_date >= X AND end_date <= Y`) excludes logs that overlap the range. Hidden disciplines are not labelled. There is no "Deleted" labelling, because delete does not exist. A copyright footer is written into every data sheet. ## 5. Spec gap list

| Requirement | Status |
|---|---|
| Login with ID + password, initial password = ID, forced change, new password ≠ ID | Partial: forced change is enforced only in the client (F-02, F-08) |
| Head: one discipline, sees and logs only its tasks | Partial: correct when the identity is honest; spoofable (F-01) |

## 6. Improvement plan

### Recommendation: targeted fixes plus one focused restructuring of the protocol layer

The DB layer, Excel service and UI widgets can be kept and fixed in place. The **server dispatch and client request/response plumbing** is the one place where the current structure blocks correctness. Identity comes from payloads, errors aren't returned, all work runs on the event loop, and replies aren't correlated. Patching each `elif` branch separately would leave 38 places to get wrong.

I will replace it with:

- a small **action registry**: each handler declares its required roles and whether it needs an authenticated session
- **one authenticated session per socket**: `LOGIN` on the long-lived connection; `IDENTIFY` removed
- a **uniform reply envelope**: `{type, msg_id, ok, error}`
- **DB work on a single worker thread** (`asyncio.to_thread` with a single-writer executor)

On the client side, `request_async` with `msg_id` futures replaces the global `response_received` broadcast. This is about 400–600 lines touched in `server.py` and `client.py`. Everything else stays targeted fixes. No rewrite and no new runtime dependencies.

Milestone order follows the audit: security and server correctness first, then data integrity, because data written before M1 cannot be trusted.

### M1: Core architecture correctness (security, server, queue)
- **Goals:** every action is authenticated and authorized on the server; the event loop never blocks; errors always reach the user; the queue loses nothing.
- **Work:**
  1. **Sessions.** `LOGIN` on the persistent `NetworkClient` connection. The server binds `user_id`, role and discipline from the DB to the socket. `IDENTIFY` is removed. On reconnect the client re-authenticates with a server-issued session token (random 32 bytes, kept in memory, expires on logout or server restart), so the password is not held.
  2. **Action registry** with a role table:
     - Head: own logs, proposals, date changes, alert responses, own lists.
     - Admin: Head accounts, projects, tasks, approvals, analytics, export.
     - COO: feed, export, alerts.
     - Super Admin: everything.

     Actions are rejected until `must_change_password` is cleared, except `CHANGE_PASSWORD`. The acting user always comes from the session; payload identity fields are ignored.
  3. **`CHANGE_PASSWORD`:** requires the session, plus the old password unless this is the forced first change on the same session. Minimum length 8, ≠ ID, no stripping.
  4. **Uniform reply envelope** for every request. Each handler is wrapped in try/except so a handler error never closes the socket. Every write handler replies.
  5. **DB on a dedicated worker thread.** Excel built off-loop. Export sent in chunks (`EXPORT_CHUNK` frames of about 512 KB plus a final frame), or `max_size` raised to 64 MB on both ends with chunking. Chunking is preferred.
  6. **Client:**
     - `request_async` with msg_id futures, so each widget gets only its own replies (fixes the duplicate Save dialogs).
     - Login made async through qasync, with no `.result()` on the GUI thread.
     - Every server-mutating action goes through the persistent queue, or is refused with a clear "offline" message.
  7. **Queue:**
     - Full UUID4 IDs.
     - Queue rows tagged with `user_id`; only the logged-in user's rows are flushed.
     - ERROR ACKs move an item to a `failed` state, shown to the Head with the reason.
     - A packet is removed from the in-memory send queue only after a successful send.
     - One in-flight flush with ordered sends.
     - Server-side idempotency also for `COO_NOTIFY` and the approve/reject actions (client-generated `request_id`).
  8. **Bootstrap:** stop seeding `admin` / `coo` / `superadmin`. On first server start with no Super Admin, a one-time random password is printed to the server console and log (forced change on first login). Alternatively, `DeskApp.exe --create-superadmin`. `--standalone` demo seeding stays, but only for a DB under a separate `data_demo/` folder.
  9. **Toasts reflect real outcomes:** "Saved" on ACK, "Queued (offline)", "Failed: reason".
- **Closes:** F-01, F-02, F-03, F-04, F-05, F-06, F-07, F-08, F-09, F-10, F-11, F-17, F-20, part of F-27 (`compare_digest`, 600k iterations on next password change).
